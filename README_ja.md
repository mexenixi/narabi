# Narabi

[English](README.md) | [日本語](README_ja.md)

Narabiは、写真、画像、スキャン書類、PDFページなどを一つの視覚的な並びとして扱い、必要な順番へ整理してから目的の形式で出力する、iPhone・iPad向けのローカル優先アプリです。

## なぜNarabiを作ったのか

Narabiは、大学で配布された資料や友人から受け取った資料について、写真とPDFを混ぜたまま順番を整えたいと考えたことから始まりました。

当初はiPhoneの「ショートカット」アプリを使って対応していましたが、その後、身内の小規模事業者も、写真とPDFが混在する書類の整理に困っていることを知りました。自分だけでなく身近な人にも必要とされるなら、より使いやすい一つのアプリとして作ろうと考え、Narabiの開発を始めました。

Narabiは、取り込んだ時点で素材を一つの完成ファイルへ変換しません。アプリ内では、それぞれを並べ替え可能なページとして扱い、出力するときに目的の形式へまとめます。この分離によって、写真、画像、スキャン書類、PDFページなどを、元のファイル形式に分けられずに整理できます。

## ファイルの境界ではなくページを扱う

```text
写真／画像／スキャン／PDFページ
               ↓
      Narabi内のページ素材
               ↓
   並べ替え・選択・補正・確認
               ↓
 PDF／JPEG／PNG／写真アプリへ出力
```

Narabiへ取り込んだ資料は、元のファイル形式にかかわらず、共通のページ素材として扱います。

上側の編集欄は、現在の出力対象とその順番を表します。現在の出力に使わないページも、すぐに削除する必要はありません。下側の素材欄へ分けて置き、後から編集欄へ戻したり、別のページと置き換えたりできます。削除したページは、完全削除するまで削除済みから復元できます。

整理したページは、編集欄の順番を使ってPDFや画像として出力できます。写真として出力する場合も、利用者が選択した順番を反映できます。

## 最も単純な操作に特化する

Narabiでは、画面へボタンを増やしすぎず、関連する機能をできるだけ少ない操作へまとめています。

ページを長押しして選択し、ドラッグして並べ替え、画面へ直接触れて位置や大きさを調整するなど、対象を見ながら感覚的に操作できることを重視しています。多くの操作を用意しながらも、それぞれの機能のためにボタンや画面を増やし続けるのではなく、すっきりした見た目の中で扱えるように設計しています。

できるだけ言語に頼らず操作できるよう、一般的な意味を想像しやすいアイコンを使用します。一方で、表示する文字を減らすことによって必要な情報が失われないよう、アクセシビリティ向けの説明や、必要な場面での文字表示も用意します。

## 用途を決めない

Narabiは、プロジェクトの用途や正しい使い方を一つに決めません。

何を取り込み、どのように並べ、どの機能を使い、どの形式で取り出すかは利用者が決めます。必要になったときに機能を探索しながら、自分に合った使い方を見つけられる道具を目指しています。

利用者が作成したプロジェクトは、利用者が削除するかアプリ自体を削除しない限り、アプリが独自の期限を決めて自動的に削除しません。しばらく使わなかった場合でも、残しておいた作業を後から再開できます。

並べ替えやページの移動などの通常操作は自動的に保存します。切り取りや重ね合わせなど、内容を個別に編集する画面では、保存またはキャンセルによって結果を確定します。

## 機能を追加するときの方針

新しい機能を追加するときも、画面へボタンを増やしすぎず、すっきりした見た目と感覚的な操作を維持することを優先します。

長押し、ドラッグ、拡大・縮小など、対象へ直接触れる操作の中へ関連機能をまとめ、現在の操作の分かりやすさを保てる範囲をNarabiの機能量の基準とします。

その範囲へ自然に収めることが難しい大きな機能は、同じアプリへ無理に詰め込まず、Mexenixiの別のアプリへ分け、必要に応じてアプリ同士を連携させる方針です。

## 製品の考え方

Narabiは、次の4つの考え方を軸にしています。

1. **元のファイル形式を別々の作業に分けず、共通のページとして扱う。** 写真、スキャン、PDFページ、対応文書を同じ作業空間で扱えます。
2. **現在の出力に使わない素材を、削除するよう強制しない。** 候補や差し替え用ページを素材欄へ残し、後から編集欄へ戻せます。
3. **正しい用途を一つに決めない。** プロジェクトの意味、保持期間、使う機能、出力方法は利用者が決めます。
4. **データと外部サービスの選択権を利用者に残す。** ローカル処理を優先し、Narabiアカウントを必要とせず、外部AIへの受け渡しは利用者が共有先を明示的に選んだ場合だけ行います。

## ローカル処理を重視する理由

Narabiは、可能な限り文書を利用者の端末内で処理します。理由はセキュリティだけではありません。ファイルの所在を利用者自身が把握しやすくし、最初に資料を受け取った端末から、そのまま整理、出力、共有できるようにするためです。

現在、文書を最初に受け取る端末がパソコンであるとは限りません。資料がメール、メッセージ、AirDrop、写真共有、クラウドストレージなどを通じて、最初にスマートフォンへ届く場合があります。

Narabiは、iPhoneやiPadで受け取った資料を、その端末上でページとして確認し、並べ替え、必要な形式へまとめ、iOSの共有機能を使って次の相手へ渡せることを目指します。

利用するための独自アカウントは必要ありません。Narabi独自の文書保存サーバーやクラウド同期サービスも使用しません。

## 利用者が共有先を選ぶ外部AI

Narabiは、特定のAIサービスをアプリへ固定的に組み込みません。

アプリ内でAI用ファイルを作成し、利用者がiOSの共有画面から使用したい外部AIを選びます。NarabiがAI用ファイルを自動的に外部へ送信することはありません。どのサービスへ何を共有するかは利用者が決めます。

外部AIから返された並べ替え結果についても、Narabiが自動的に適用することはありません。セッション、ページID、重複、欠落、形式を検証し、利用者が内容を確認した後にだけ順番へ反映します。

外部サービスへ共有した後は、そのサービスの利用規約とプライバシー方針が適用されます。機密情報を含む場合は、共有前にファイルの内容と共有先を確認する必要があります。

## 品質確認と検証

Narabiは、画面操作の調停と、テスト可能なPolicy、Service、Loader、Engine、永続化、描画処理を分離しています。自動単体テストでは、プロジェクト操作、取込み経路、保存、ページ編集、レイアウト、重ね合わせ、出力関連の規則を確認します。

GitHub Actionsでは、Ubuntu上のリポジトリ監査と、macOSのiPhone Simulator上での`NarabiTests`単体テストを実行します。直近にローカルで確認したテスト件数、Releaseビルド結果、検証範囲は[Docs/TESTING.md](Docs/TESTING.md)に記録します。これらの確認は不具合の再発を減らすためのもので、すべての端末、ファイル、利用条件を網羅するという意味ではありません。

## 翻訳確認への協力

翻訳への協力に、アプリのビルドやソースコードの編集は必要ありません。

- まず[ローカリゼーションガイド](Docs/Localization/README.md)を確認してください。
- [言語別アプリ名](Docs/Localization/APP_NAMES.md)を確認できます。
- 用語と画面上の文脈は[用語集](Docs/Localization/GLOSSARY.md)にあります。
- [言語別の閲覧用ファイル](Docs/Localization/Generated/)で現在の文面を読んだり検索したりできます。
- 修正案や新しい言語の提案は[Translation Issue](https://github.com/mexenixi/narabi/issues/new?template=translation.yml)から送れます。

直訳より、意味と使われる場面に合う自然な現地表現を優先します。母語話者や日常的にその言語を使う方の確認を特に歓迎します。機械支援による提案も、その旨が明示されていれば歓迎します。翻訳の正本はXcodeの文字列カタログです。

### 現在未対応の言語も歓迎します

現在Narabiに含まれていない言語についても、提案を歓迎します。すべての文字列を一度に用意したり、アプリをビルドしたり、Xcodeの文字列カタログを編集したり、Pull Requestを作成したりする必要はありません。

Translation Issueで **Add a new language** を選び、ロケールコード、言語名、必要に応じた地域差、文字方向、分かる範囲の提案文を記載してください。一部の文面だけの提案、用語の確認、アプリ名の提案、今後作成される翻訳案の確認協力だけでも役立ちます。まだ存在しないロケールでは **Current text** を空欄にし、**Reason and usage context** に地域での用法、語調、文字体系、その他の要件を記載できます。

採用できる提案をもとに、管理者が文字列カタログへの追加と閲覧用ファイルの生成を行えます。新しいロケールを完成と扱う前に、画面文言、権限説明、現地語のアプリ名、App Store掲載文、App内課金の商品名と説明、レイアウト、文字方向、代表的な実機画面を確認します。この段階的な仕組みにより、SwiftやXcodeの知識がなくても言語協力へ参加できます。

## ビルド

1. Xcodeで`Narabi.xcodeproj`を開きます。
2. **Signing & Capabilities**で自分のApple Development Teamを選択します。
3. Bundle Identifierが自分のアカウントで使用可能か確認します。
4. iPhoneまたはiPadを選び、ビルドします。

公開リポジトリには、元の開発者のTeam設定、証明書、Provisioning Profile、秘密鍵を含めません。
